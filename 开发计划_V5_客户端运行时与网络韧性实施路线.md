# 3. 当前必须保持的核心不变量

## 3.1 Authoritative state

private authoritative PlayerView 只通过：

```text
client:state
```

进入：

```text
ClientSession
→ AuthoritativeClientStateStore
→ UI rendering
```

`room:state` 仍然是 production Web 的 public / Host room UI contract，当前必须保留。

## 3.2 Reconnect

Reconnect 的 source of truth 是 authoritative state：

```text
reconnect
  ↓
identity restored
  ↓
authoritative PlayerView sync
  ↓
revision reconciliation
```

不是：

```text
reconnect -> replay full realtime history
```

## 3.3 Connection state

Socket connected 不等于 game session synchronized。

标准路径：

```text
Connecting / Reconnecting
        ↓ transport open
Syncing
        ↓ authoritative PlayerView accepted
Connected
```

## 3.4 Revision / generation

- newer revision：apply；
- equal revision：duplicate，合法；
- lower revision：stale；
- stale generation：ignore；
- reconnect 可以推进 generation，但保留最后可信 PlayerView，直到新 generation 同步完成。

## 3.5 Transient realtime effects

```text
client:event
```

承载 transient effects / lifecycle events。

普通 vibration / audio：

- 可以丢失；
- 可以重复；
- 可以乱序；
- malformed transient effect 必须 nonfatal；
- unsupported browser capability 必须安全 no-op；
- reconnect 不要求 replay 全部 transient history。

Effect Outbox 仍属于 R1，不提前混入 E3。

# 10. E3.1 — WeChat transport / ClientSession boundary audit ✅

审计日期：2026-09-27。

## 10.1 审计结论

### A. `ClientSession` 的 source boundary 已经 platform-neutral

已确认：

- `src/client/runtime/*` 不依赖 DOM、Socket.IO、Cloudflare runtime 或 `wx`；
- generation、authoritative PlayerView revision reconciliation、reconnect/resync policy 与 transient event 分流都可以复用；
- browser foreground/background 已经通过 `BrowserSessionLifecycle` 外置，证明 lifecycle 不属于 `ClientSession`。

因此 **不需要为微信复制第二套 ClientSession/FSM/state store**。

### B. 当前 `ClientRealtimeTransport` 的行为合同还不能直接承载 Cloudflare / WeChat Raw WebSocket

关键 mismatch：

```text
ClientSession.start()
  -> transport.connect(generation)
  -> transport open
  -> synchronize(credentials, generation)
```

但 Cloudflare 已确定的安全连接流程是：

```text
resume credentials
  -> POST websocket-ticket
  -> one-time ticket
  -> WebSocket upgrade
```

即 `resumeToken` 必须在 socket open **之前**可供 transport 换 ticket。

因此当前 interface 虽然 source-level transport-neutral，但存在 Socket.IO 历史假设。E3.2a 必须先建立 **pre-connect credential/ticket seam**。最小改法优先采用：

```ts
connect(credentials, generation)
```

先保留现有 `synchronize(credentials, generation)` 以减少 E2 Web 路径 churn；等第二种 transport 真实实现后再判断是否值得进一步收敛签名。

### C. Cloudflare server 已有基础能力，但 Raw WebSocket stable client wire 仍缺失

已有：

- resume token -> one-time WebSocket ticket；
- Hibernation WebSocket stable player identity；
- Node / Cloudflare command semantic parity；
- Cloudflare private PlayerView projection。

仍缺：

- Raw WebSocket `client:command` framing / parsing；
- command ACK / request correlation；
- explicit authoritative sync request/response；
- `client:state` push wire delivery；
- `client:event` push wire delivery；
- malformed frame / protocol-version failure contract。

当前 `GameRoomDurableObject.webSocketMessage()` 只处理 `session:whoami`，所以 E3.2c 之前必须先完成 E3.2b；微信 adapter 不得私自发明另一套 wire format。

### D. 微信 lifecycle / storage / capability ownership

```text
WeChat composition root
  ├─ WeChatRealtimeTransport
  │    └─ wx.connectSocket / SocketTask / ticket exchange
  ├─ WeChatSessionLifecycle
  │    └─ foreground -> Connected: resync
  │                     Disconnected: reconnect
  ├─ WeChatSessionCredentialStore
  │    └─ local storage roomId/playerId/resumeToken
  └─ WeChatClientEffects
       └─ vibration / semantic audio
```

约束：

- persistent resume credential storage 不属于 `ClientSession` 或 transport；
- app/page foreground/background 不进入 core/runtime shared；
- transport close/error 仍通过 generation-tagged listener 回报；
- foreground recovery 复用 `ClientSession.resync()/reconnect()`，不复制 recovery rule。

### E. `room:state` 不进入当前 E3.2 transport foundation

现有 `ClientSession` / `AuthoritativeClientStateStore` 明确只拥有 private `scope: "player"` PlayerView。

因此：

- E3.2–E3.5 transport/session PoC 可使用已经存在的 room/player/resume credentials，先证明 private PlayerView + command + reconnect；
- 不把 Web raw `room:state` 事件直接复制到微信；
- E3.6 minimal lobby 前，再从第二客户端真实 UI 需求提取 transport-neutral public room projection/delivery contract；
- 不为了 lobby 提前把 public room state 塞进 PlayerView store。

### F. effect contract 有一个非阻塞的后续问题

audio 已经是 semantic cue；vibration 仍携带 browser-friendly numeric pattern。

微信 vibration capability 不应被迫精确模拟浏览器 pattern。E3.5 需要基于真实微信能力决定：

- 保留 pattern 但允许 platform degradation；或
- 上提为 semantic vibration cue。

这不阻塞 E3.2 transport foundation。

# 14. BotC Expansion

BotC 已从“远期扩展”提升为 **MG0 完成后的立即主线**。进入条件只要求：

```text
W3D3 game-neutral identity recovery complete
+ MG0 second-game admission hardening complete
+ existing WeChat/Cloudflare shared client runtime remains green
```

**W3E Production Web authority cutover 不再是 BotC 前置条件。** 当前产品优先级是尽快利用已经通过真机验证的 Native WeChat + Cloudflare 基础进入 BotC，而不是先完成 Web 产品迁移。

微信发布形态采用两个 game-specific thin-client shells，工作名：

```text
骏骏桌游-狼人
骏骏桌游-血染
```

它们共享同一套 `ClientSession`、Raw WebSocket、identity/recovery、Room Runtime、Cloudflare Worker/DO 和 shared client protocol 基础；只分离具体游戏的 Setup、页面、命令、projection、资源与主持体验。不得复制共享 runtime/backend 形成两套服务器或两套 reconnect 实现。

房间创建时固定 `gameType`；Lobby 不提供跨游戏切换。不同游戏客户端加入不匹配房间时应得到明确的 wrong-game/product mismatch 结果，而不是尝试转换房间状态。

MG0 必须先关闭以下当前 Werewolf 泄漏点：

- `GameRoomDurableObject` 的 `gameType: "werewolf"`、狼人默认 config 与 max-player bootstrap 硬编码；
- shared/Cloudflare protocol bridge 对 `GameState` / `GameConfig` / `WerewolfInteraction` 的具体依赖；
- concrete Werewolf lifecycle / command / projection dispatch 与 room/runtime authority 混在一起；
- `isHost` 同时承担 Room Owner 与 Game Moderator/Storyteller 的隐式语义。

复用平台概念：

```text
GameModule
PendingInteraction
PlayerView
HostView
Command
Effect
Revision
ClientSession
```

MG0 建立最小明确 `GameCatalog`：

```text
GameCatalog
  ├─ Werewolf
  └─ BotC
```

BotC 内部从一开始必须区分三个责任层：

```text
Rules Engine
  -> 决定真实状态与规则是否合法

Information / Registration Engine
  -> 从真实状态生成规则允许呈现的信息候选

Storyteller Decision Engine
  -> 只对合法候选做推荐 / 排序 / trace / replay
```

硬约束：

- Storyteller recommendation 不是 authority，不直接 mutation Room Runtime；
- Room Owner 与 Game Moderator/Storyteller 权限分离；真人说书人可获得游戏所需秘密视图，但房主不会因此自动获得秘密上帝视角；
- runtime 不理解醉酒、中毒、注册、红鲱鱼、恶魔 bluff 等 BotC 语义；
- DecisionTrace / policy version 应从第一版 recommendation algorithm 起进入设计；
- EvidenceLab / 真人对局证据用于离线 calibration / replay，不成为在线规则正确性的外部依赖；
- 先实现 Trouble Brewing，等第二个剧本真实验证重复需求后再上提通用 abstraction；
- 不提前为未知角色能力设计大型 DSL。

# 18. 开发纪律

继续采用：

```text
inspect design + current code
→ choose one logical batch
→ contract / regression tests
→ production integration
→ typecheck
→ full test

→ final diff audit

```

原则：

- 不因为某 legacy event “看起来旧”就删除；
- production Web 不应同时消费新旧两条等价 effect/state path；
- public room state 与 private PlayerView 分开判断；
- recovery correctness 优先于 transport cleanup 的整齐程度；
- platform adapter 不复制 authoritative game logic；
- 一个逻辑批次可以包含多个同构小改动，减少 branch / PR / CI 开销；
- 重大架构变化仍单独 PR；
- GitHub connector 的 whole-file write 必须用 compare + CI 审计。

最终原则：

> **网络层越复杂，游戏规则层越应该保持简单；客户端越多，authoritative source of truth 越应该集中。**
