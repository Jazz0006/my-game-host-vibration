# E3.7 Real-device foreground/background validation

## Goal

E3.7 does not add new Werewolf rules or expand the native UI. Its purpose is to prove that the E3.1-E3.6 client stack survives actual Mini Program lifecycle and network transitions on real devices.

```text
wx runtime
  -> realtime capability port
  -> effect capability port
  -> lifecycle signal port
  -> ClientSession / authoritative PlayerView
```

The code in this PR adds the concrete `wx` capability binding. The physical-device cases below remain manual validation items until they are executed on actual hardware.

## Automated acceptance

The repository tests should prove:

- one wx-like object can supply the existing realtime transport port;
- vibration/audio capabilities remain optional and nonfatal;
- `onAppShow` is adapted without leaking launch/show payloads into ClientSession;
- the same wrapped app-show listener can be detached correctly;
- network status is forwarded as an observation only;
- reconnect/resync policy is not duplicated in this binding;
- no game rules, revision reconciliation, command retry, or effect durability are implemented here.

## Composition after E3.1 is merged

```text
const bindings = createWeChatMiniProgramBindings(wx)

const session = createWeChatClientSession(
  bindings.realtime,
  credentials,
  transportOptions,
)

attachWeChatSessionLifecycle(session, bindings.lifecycle)
attachWeChatClientEffects(session, bindings.effects, effectOptions)
```

`createWeChatMiniProgramBindings()` deliberately exposes structural ports. E3.1 remains the owner of the decision:

```text
Connected + foreground/network recovered -> resync()
Disconnected + network recovered         -> reconnect()
transitioning states                     -> no-op
```

## Manual device matrix

Run the minimal E3.6 lobby/seer slice with server revision visible in diagnostic logging.

### A. Foreground -> another app -> foreground

- [ ] Start in `Connected` with a known revision.
- [ ] Switch to another app long enough for the Mini Program to enter background.
- [ ] Advance authoritative server state while the Mini Program is backgrounded.
- [ ] Return to WeChat.
- [ ] If the physical socket survived, session enters `Syncing` on the same generation and applies the latest PlayerView.
- [ ] If the socket was closed, transport reports `Disconnected`; recovery obtains a new ticket/socket and advances generation before sync.
- [ ] No missed `client:event` history is replayed.

### B. Screen lock -> unlock

- [ ] Start during lobby/waiting state.
- [ ] Lock the phone screen.
- [ ] Advance authoritative state on the server.
- [ ] Unlock and return to the Mini Program.
- [ ] Latest authoritative revision is eventually rendered.
- [ ] No stale pre-lock socket frame can overwrite the newer generation/revision.

### C. Network loss -> recovery

- [ ] Disable connectivity while `Connected`.
- [ ] Confirm network-loss notification alone does not locally invent a disconnect transition.
- [ ] Confirm actual WebSocket close/error drives `ClientSession` to `Disconnected`.
- [ ] Restore connectivity.
- [ ] Confirm a new short-lived WebSocket ticket is requested when reconnect is required.
- [ ] Confirm authoritative sync completes before status returns to `Connected`.

### D. Wi-Fi -> cellular and cellular -> Wi-Fi

- [ ] Begin on Wi-Fi with a synchronized session.
- [ ] Disable Wi-Fi so the device moves to cellular.
- [ ] Observe whether the existing socket survives or closes on the tested WeChat/device combination.
- [ ] In either case, the final PlayerView revision must equal the server's current revision.
- [ ] Repeat cellular -> Wi-Fi.

### E. Lost command ACK during network transition

- [ ] Submit the E3.6 seer target.
- [ ] Interrupt connectivity after server commit but before ACK reaches the client.
- [ ] Restore connectivity and complete authoritative sync.
- [ ] Confirm E3.4 resends the same `commandId` only after `Connected`.
- [ ] Confirm the transport request id is new.
- [ ] Confirm the server reports replay/idempotent outcome and does not execute the action twice.

### F. Native effects

- [ ] Receive the wake vibration on a real device.
- [ ] Verify duplicate vibration delivery is annoying at worst, never state-changing.
- [ ] Verify missing/blocked vibration capability does not affect the session.
- [ ] Verify configured semantic audio cue plays when allowed by the device/runtime.
- [ ] Background suspension or failed audio playback must not change authoritative state.

## Exit criteria

E3.7 is complete only after:

1. automated binding tests pass in CI; and
2. at least one iOS device and one Android device pass A-E; and
3. vibration/audio behavior is observed on at least one supported physical device; and
4. any platform-specific deviations are documented without moving game authority into the client.

Until those manual checks are executed, this PR should be treated as **E3.7 validation-ready**, not as proof that real-device validation has already passed.
