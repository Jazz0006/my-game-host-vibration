# E3.7 Real-device foreground/background validation

## Goal

E3.7 does not add new Werewolf rules or expand the native UI. Its purpose is to prove that the E3.1-E3.6 client stack survives actual Mini Program lifecycle and network transitions on real devices.

```text
wx runtime
  -> realtime capability port
  -> effect capability port
  -> lifecycle signal port
  -> ClientSession / authoritative PlayerView
```

The code in this PR adds the concrete `wx` capability binding plus a dev-only Mini Program validation harness. Real-device results are recorded below as they are executed.

## Automated acceptance

The repository tests should prove:

- one wx-like object can supply the existing realtime transport port;
- vibration/audio capabilities remain optional and nonfatal;
- `onAppShow` is adapted without leaking launch/show payloads into ClientSession;
- the same wrapped app-show listener can be detached correctly;
- network status is forwarded as an observation only;
- reconnect/resync policy is not duplicated in this binding;
- no game rules, revision reconciliation, command retry, or effect durability are implemented here.

## Composition after E3.1 is merged

```text
const bindings = createWeChatMiniProgramBindings(wx)

const session = createWeChatClientSession(
  bindings.realtime,
  credentials,
  transportOptions,
)

attachWeChatSessionLifecycle(session, bindings.lifecycle)
attachWeChatClientEffects(session, bindings.effects, effectOptions)
```

`createWeChatMiniProgramBindings()` deliberately exposes structural ports. E3.1 remains the owner of the decision:

```text
Connected + foreground/network recovered -> resync()
Disconnected + network recovered         -> reconnect()
transitioning states                     -> no-op
```

## Dev harness

The dev-only harness lives under:

```text
dev/wechat-e3-device/
```

Prepare generated runtime files with:

```bash
npm run prepare:wechat-device
```

For repeated authoritative-revision testing, use:

```bash
npm run e3:revision -- <revision>
```

The harness intentionally keeps room/player/resume credentials in Mini Program local storage and out of Git. It exposes connection status, generation, authoritative revision, failure diagnostics, lifecycle/network logs, manual reconnect/resync, and short/long vibration probes.

## 2026-08-19 Android validation checkpoint

Physical device:

```text
Device: Xiaomi-22101320G
OS/API shown by WeChat DevTools: 34
WeChat: 8.0.72
Mini Program base library: 3.17.1
Network: Wi-Fi
Backend: https://my-game-host-vibration.jazz-zeng.workers.dev
```

Setup findings:

- Mini Program `request` and `socket` legal domains must be configured for the Worker URL on real hardware; the DevTools "do not validate domains" option was not sufficient for this path.
- `request` domain configured as `https://my-game-host-vibration.jazz-zeng.workers.dev`.
- `socket` domain configured as `wss://my-game-host-vibration.jazz-zeng.workers.dev`.
- An initial `invalid session credentials` failure was traced to the resume token being pasted three times in the real-device input, not to transport/session code.
- The dev harness input sizing was increased afterward because the original credential fields clipped text on device.
- Physical initial connection reached authoritative `Connected` state successfully.

Observed authoritative recovery sequence during this session:

```text
initial physical connection: Connected gen=1 rev=2
manual resync/recovery:      Connected gen=2 rev=3
app background recovery:    Connected gen=3 rev=4
screen lock recovery:       Connected gen=4 rev=5
network-loss recovery:      latest server revision restored after connectivity returned
```

The generation increments above are legal reconnect outcomes. The important invariant observed on each recovery path is that the final PlayerView revision converged to the current authoritative server revision before the usable connected state was restored.

### E. Lost command ACK during network transition

Status: **next real-device validation item**.

Use deterministic fault injection rather than relying on hand-timed network interruption.

Expected flow:

```text
submit command with commandId A
  -> server commits action A
  -> first ACK is intentionally dropped
  -> client reconnects/synchronizes as needed
  -> E3.4 retries semantic command with the same commandId A
  -> transport request id is new
  -> server reports replay/idempotent result
  -> action is not executed twice
```

- [ ] Add/enable dev-only deterministic lost-ACK injection.
- [ ] Submit the E3.6 seer target.
- [ ] Confirm server commit occurs once while the first ACK is dropped.
- [ ] Restore/recover connectivity if required and complete authoritative sync.
- [ ] Confirm E3.4 resends the same `commandId` only after `Connected`.
- [ ] Confirm the transport request id is new.
- [ ] Confirm the server reports replay/idempotent outcome and does not execute the action twice.

### F. Native effects

- [x] Long vibration through the E3.7 effects binding/harness is clearly perceptible.
- [x] Short vibration through the E3.7 effects binding/harness works but is very light on this device.
- [x] The short/long behavior is treated as a device capability/UX difference, not authoritative state.
- [ ] Verify duplicate vibration delivery is annoying at worst, never state-changing.
- [ ] Verify missing/blocked vibration capability does not affect the session on physical hardware.
- [ ] Verify configured semantic audio cue plays when allowed by the device/runtime.
- [ ] Background suspension or failed audio playback must not change authoritative state.

1. automated binding tests pass in CI; and
2. at least one iOS device and one Android device pass A-E, except a temporarily unavailable network-path case may remain explicitly documented until appropriate hardware is available; and
3. vibration/audio behavior is observed on at least one supported physical device; and
4. any platform-specific deviations are documented without moving game authority into the client.

E3.7 is now **partially real-device validated** rather than merely validation-ready, but it is not complete yet. Scenario E, semantic audio, iOS coverage, and the deferred cellular transition remain outstanding.
