# E3.6 — Minimal WeChat Lobby + Seer Night-action Vertical Slice

## Goal

Prove that the native WeChat client infrastructure built in E3.1–E3.5 can support one real Werewolf player flow without copying server game logic or the existing Web UI.

The slice is intentionally narrow:

```text
existing reconnect credentials
        ↓
ClientSession / Raw WebSocket sync
        ↓
authoritative lobby PlayerView
        ↓
authoritative seer_action PlayerView
        ↓
client:event wake effect
        ↓
player selects one authoritative target
        ↓
werewolf.submitSeerTarget
        ↓
command ACK / reconnect-aware retry
        ↓
authoritative seer_result PlayerView
```

## New client boundary

`WeChatWerewolfVerticalSlice.ts` is a page-controller/view-model boundary, not a game engine and not a final WeChat Page implementation.

It composes:

- `createWeChatClientSession()`
- `attachWeChatClientEffects()`
- `sendWeChatCommandWithReconnectRetry()`
- stable `werewolf.submitSeerTarget`

The controller projects only fields already present in the private authoritative PlayerView:

- `phase`
- `mode`
- `roleName`
- `actionId`
- `targets`
- `checkedPlayer`
- `checkedAlignment`

It does not calculate the active role, night order, legal target rules, alignment, or phase transitions.

## Lobby boundary

E3.6 does **not** add native room creation/join/account flows. The PoC starts from existing stable reconnect credentials and proves that an authoritative `{ phase: "lobby", mode: "lobby" }` PlayerView can render a native lobby screen model.

Session entry / room-management protocol remains a separate concern and is not expanded merely to make the PoC look like a complete product.

## One night action

The selected action is the Seer target submission because it is the smallest single-player night interaction:

```text
mode = seer_action
actionId = authoritative action id
targets = authoritative target list
```

The client sends:

```text
werewolf.submitSeerTarget
```

using the current authoritative `actionId` and a selected target from the current authoritative `targets` list.

The server remains responsible for validating and applying the command. The client-side target-list check is only a stale/invalid UI guard; it does not recompute Werewolf rules.

## Effect integration

The same controller attaches the E3.5 effect adapter, so a `client:event` wake effect can vibrate the WeChat device without changing authoritative state.

Missed or failed effects remain best-effort and are not replayed or durably queued.

## Explicit non-goals

E3.6 does not add:

- WXML/WXSS visual design
- native room creation or player join
- every Werewolf role/action
- Host screens
- public `room:state`
- local Werewolf rule/phase logic
- offline command queues
- durable effect delivery
- BotC support
- production cutover

## Acceptance

The focused PoC must prove:

1. authoritative sync can render lobby;
2. a transient wake effect reaches the WeChat vibration adapter;
3. authoritative `seer_action` renders its target list;
4. selecting a target creates the stable `werewolf.submitSeerTarget` envelope with authoritative `actionId`;
5. command ACK returns through the E3.4 retry boundary;
6. only the subsequent authoritative `client:state` changes the page to `seer_result`;
7. a target absent from the authoritative target list is not sent.

E3.7 remains the first real-device foreground/background validation phase.
