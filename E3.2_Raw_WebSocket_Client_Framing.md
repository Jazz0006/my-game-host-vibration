# E3.2 Raw WebSocket Client Framing

This increment establishes the minimum stable client framing required before a native WeChat client can share `ClientSession` with the Web client.

## Scope

- versioned Raw WebSocket request / response / push frames;
- `client:sync-state` request returning one authoritative PlayerView delivery;
- `client:command` request returning a correlated command ACK;
- post-command authoritative `client:state` pushes to connected room members;
- a minimal `WeChatRealtimeTransport` using WeChat-style request/socket APIs;
- short-lived WebSocket ticket exchange before socket upgrade.

## Boundaries intentionally preserved

- `ClientSession` and `ClientRealtimeTransport` are unchanged;
- game rules and command authority stay in the shared authoritative runtime;
- `room:state` remains a Web/public-host contract and is not copied into WeChat;
- transient effect durability/replay remains deferred to R1;
- command retry remains deferred to E3.4;
- vibration/audio capability mapping remains deferred to E3.5;
- no WeChat UI is added.

## Wire model

```text
client request
  { protocolVersion, kind: "request", requestId, type, payload }

server ACK/error
  { protocolVersion, kind: "response", requestId, ok, ... }

server authoritative/transient push
  { protocolVersion, kind: "push", type: "client:state" | "client:event", payload }
```

The request ID correlates command/sync completion only. Authoritative state remains a separate push/response payload and is reconciled by `ClientSession` using revision + generation.
