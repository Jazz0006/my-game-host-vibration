# E3.4 Command ACK / Retry PoC

## Goal

Prove that a native WeChat client can safely recover from the ambiguous window where a semantic command was committed by the authoritative server but its correlated transport ACK was lost.

## Retry model

```text
ClientCommandEnvelope(commandId = stable)
        ↓
Raw WebSocket request(requestId = transport-local)
        ↓
server commits command + durable C3 receipt
        ↓
ACK lost / socket closes
        ↓
ClientSession reconnect + authoritative sync
        ↓ Connected
retry same ClientCommandEnvelope
        ↓
new Raw WebSocket requestId
        ↓
server C3 replay by same commandId
```

The client must preserve `commandId`; it must not preserve or reuse Raw WebSocket `requestId`.

## Boundary

`sendWeChatCommandWithReconnectRetry()`:

- retries only after a connectivity-loss path leaves the session Disconnected / Reconnecting / Syncing;
- waits until the shared ClientSession is Connected again before resending;
- resends the exact same semantic command envelope;
- does not initiate reconnect itself;
- does not retry a definitive server command error while the session remains Connected;
- defaults to one reconnect retry.

Server idempotency remains owned by the existing C3/D5 command receipt runtime. No new game-specific dedupe state is introduced on the WeChat client.

## Deferred

- generalized offline command queue;
- durable client-side command persistence across process termination;
- exponential backoff / retry scheduling;
- background delivery;
- effect ACK/outbox reliability (R1).
