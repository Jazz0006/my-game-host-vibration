---

# 1. 目标

本项目已经从“单机主持工具”进入“多人、实时、服务端权威、多个客户端共同参与”的产品形态。真机测试不能继续沿用单设备逐按钮验收作为主要 correctness 证据。

本路线建立四类互补证据：

1. **纯逻辑 / 权威状态测试**：证明规则与 authoritative state 正确；
2. **虚拟多人协议测试**：证明多个客户端对同一房间的状态、权限、revision、重连与幂等最终收敛；
3. **少量真实客户端 UI / lifecycle 测试**：证明客户端 composition、页面与平台 capability 接线正确；
4. **两台真机 + N 个虚拟玩家 / 最终全桌真人验收**：证明真实微信、真实网络、震动与桌面体验可靠。

核心目标不是“模拟很多手机”，而是证明：

> 同一个 authoritative room 在并发、掉线、重连、切后台、网络切换和不同视图权限下，所有客户端最终得到正确且不泄密的状态。

---

# 2. 与当前架构的关系

本测试路线必须服从现有 ownership：

```text
Room Runtime
  -> membership / identity / revision / command / reconnect / persistence / delivery

GameModule
  -> game rules / setup / sequencing / interaction / projections

ClientSession
  -> generation / sync / authoritative state reconciliation

Platform adapter
  -> Socket.IO / Raw WebSocket / WeChat lifecycle / vibration / audio
```

测试工具不得建立第二套游戏规则、第二套 projection、第二套 reconnect 规则或第二套 room state owner。

特别保持：

- stable `playerId` 不等于 socket identity；
- `commandId` 负责 logical command idempotency；
- request correlation 与 `commandId` 分离；
- reconnect 以 authoritative snapshot / PlayerView 为真相，不依赖 replay 全部 transient events；
- private PlayerView / moderator-secret / public room projection 的隐私边界不得为了测试方便而放宽；
- Room Owner 与 BotC Moderator/Storyteller 是不同 authority。

# 5. Multiplayer invariants

测试框架必须优先表达“长期不变量”，而不是大量 UI 细节。

## 5.1 Revision / convergence

- authoritative room revision 单调前进；
- 同一 generation 的 lower revision 不得覆盖 newer state；
- equal revision 可以合法重复；
- reconnect 后客户端最终必须收敛到服务器当前 revision；
- 一名玩家掉线不能阻止其他成员正常推进，除非具体游戏规则明确要求；
- fan-out 完成后，每个在线客户端必须获得属于自己的 projection，而不是共享错误 viewer projection。

## 5.2 Identity / generation

- stable player identity 不能由 socket connection identity 替代；
- resume 后必须回到原 player，而不是产生 duplicate player；
- old generation 的 late state/event/ACK 必须被 fence；
- session replacement / reconnect 不得让两个 active generation 同时修改同一客户端状态；
- identity credential rotation 后旧 credential 的行为必须符合现有 authoritative contract。

## 5.3 Command idempotency

- retry 同一个 logical command 必须复用同一 `commandId`；
- transport retry 可以更换 requestId；
- replay 不得二次推进 revision；
- duplicated delivery 不得二次执行 game mutation；
- application rejection 不应被 transport 层无限重试。

## 5.4 Privacy

- server authoritative state 不能直接下发给普通 player；
- PlayerView 不得携带其他玩家 secret；
- BotC actual role 与 shown role 的 viewer contract 必须显式测试；
- moderator-only field 不得进入 public/player projection；
- room-management authority 不得隐式升级为 game-secret authority。

## 5.5 Lifecycle

- transport open != synchronized；
- foreground 后必须 resync/reconnect 到 authoritative truth；
- temporary network loss 不应清空最后可信 state；
- malformed/stale transient effect 不得破坏 authoritative state；
- reconnect 不要求 replay 全部 transient history。

实现前 T0 审计后确定最终目录；优先考虑：


如果现有 runtime test helper 已有更合适 owner，则复用，不为了目录整齐建立平行 abstraction。

- BotC role rules；
- “下一夜应该叫醒谁”；
- 如何计算 PlayerView；
- 如何推进 authoritative revision；

它只表达客户端能做的事和能观察到的公开状态。

## 6.3 Game-specific scenario adapter

如确有需要，建立很薄的 scenario helper：

```text
tests/multiplayer/games/werewolf/*
tests/multiplayer/games/botc/*
```

这些 helper 可以构造 semantic command，但不得复制 GameModule 规则。

# 7. 首批标准场景

## S1 — Room bootstrap convergence

```text
create room
-> N players join
-> all clients synchronize
-> assert same room revision
-> assert each viewer identity/projection correct
```

## S2 — Concurrent join fan-out

多名玩家快速加入：

- host 无需 refresh 即看到成员；
- 已在线玩家最终看到相同 membership；
- 不产生 duplicate seat/player；
- revisions 单调。

## S3 — Disconnect while room continues

```text
P3 disconnect
-> other clients perform legal state changes
-> P3 reconnect/resume
-> P3 receives current authoritative revision
-> stale old-generation data cannot overwrite it
```

## S4 — Command retry/idempotency

```text
send command
-> drop/ignore first ACK
-> retry same commandId with new requestId
-> server returns replay
-> revision advances only once
```

## S5 — Full transport restart/resume

客户端完全销毁连接对象，再用 persisted roomId/playerId/resumeToken 恢复：

- same player identity；
- no duplicate member；
- latest authoritative state restored。

## S6 — Privacy matrix

针对同一 authoritative state：

```text
normal player
special/Drunk player
moderator/storyteller
public/room projection
```

分别断言允许字段与禁止字段。

## S7 — Partial connectivity

- 一个玩家高延迟/掉线；
- 其余在线；
- room authority 继续稳定；
- 恢复后最终 convergence。

## S8 — Duplicate/stale delivery

人为注入：

- duplicate state；
- lower revision；
- stale generation；
- late ACK；
- duplicate transient event。

客户端必须符合现有 store/FSM 语义。

# 8. BotC 专项

B0B 及后续 BotC 主线会不断增加 secret state，因此测试框架必须支持但不能阻塞 B0B。

BotC-specific multiplayer scenario 在对应 production contract 稳定后再接入。

优先覆盖：

1. setup 后不同玩家只看到自己的 shown role；
2. Drunk：
   - authoritative actual role 保持服务器内部真实值；
   - 玩家只看到 shown role；
   - Storyteller/Moderator 可见其授权信息；
3. Baron 等 setup mutation 不因 viewer projection 泄露隐藏 setup 事实；
4. first-night information 只送给正确 actor；
5. disconnected actor reconnect 后恢复当前合法 interaction，而不是 replay 已过期秘密；
6. PublicView 不泄漏 alignment / actual role / storyteller-only decision trace。

---

# 9. Werewolf 回归用途

同一 harness 也必须用于现有 Werewolf，以证明它是平台测试工具而不是 BotC 专用工具。

首批 Werewolf smoke 可以覆盖：

- create/join/start；
- one night action；
- action-alert event；
- retry/replay；
- reconnect；
- abort-to-lobby/recovery 中至少一条现有稳定路径。

如果 harness 只能测试 BotC，则说明 abstraction 层级选错。

# 10. 故障注入策略

测试 harness 应提供显式 fault controls，而不是随机制造不稳定测试。

建议能力：

```text
dropNextResponse()
delayNextState()
disconnectTransport()
ignoreNextAck()
deliverDuplicateFrame()
deliverStaleGenerationFrame()
```

原则：

- 默认 deterministic；
- seed / scenario step 可记录；
- CI 不依赖随机 timing 才能复现；
- timeout 只作为防死锁，不作为主要正确性断言。

后续如做 randomized chaos，应建立在 deterministic suite 已稳定之后。

---

# 11. Trace / 可诊断性

多人测试失败如果只显示“expected revision 8, got 7”会很难排查。

每个 TestRoomClient 应能记录 bounded trace：

```text
timestamp/order
client label
generation
transport state
requestId
commandId
received revision
applied/ignored reason
event type
connection lifecycle
```

失败报告优先输出最近有限条记录，禁止无限 log。

Trace 只记录测试需要的元数据；不要打印长期 resume token 或不必要 secret。

# 13. 真机标准测试卡

## D1 — Foreground/background

1. 进入房间；
2. 记录当前 revision / player；
3. 微信切后台；
4. 其他客户端推进状态；
5. 返回；
6. 验证 resync/reconnect；
7. 验证无 duplicate player、无旧状态覆盖。

## D2 — Airplane mode

1. 正常连接；
2. 开飞行模式；
3. 等待明确 disconnected；
4. 其他客户端推进；
5. 关闭飞行模式；
6. 验证自动恢复 authoritative current state。

## D3 — Process restart

1. 正常加入；
2. 完全退出小程序/微信进程允许范围内结束 session；
3. 重新进入；
4. “继续上次房间”；
5. 验证同一 player identity、最新 revision、无 duplicate member。

## D4 — Network switch

Wi-Fi -> cellular 或反向切换，验证：

- reconnect；
- same player；
- latest authoritative state；
- pending action 恢复符合当前游戏 contract。

## D5 — Vibration

只验证平台 rendering：

- short heavy 可感知；
- long 可感知；
- effect adapter failure 不影响 session/state；
- 游戏事实不能依赖用户是否实际感觉到某次震动。

# 15. Playwright 的位置

Playwright 可在未来承担 Web UI 多上下文测试，例如：

```text
BrowserContext A = host
BrowserContext B = player 1
BrowserContext C = player 2
```

但它不是当前第一优先级。

原因：

- 本项目最主要风险在 authoritative multiplayer semantics、privacy、reconnect、revision convergence；
- 这些应由 protocol-level harness 更稳定、更快地覆盖；
- 微信 native lifecycle/震动也无法由 browser UI test 完整代表。

因此：

> 先 TestRoomClient，后按真实 UI 回归需求决定是否加入 Playwright。

# 19. 完成标准

本测试战略达到成熟状态时，应能做到：

1. 一条命令建立 1 host + 8/9 virtual players；
2. deterministic 地跑 create/join/start/sync/reconnect；
3. 自动验证 all-client convergence；
4. 自动验证 private/public/moderator privacy；
5. 自动验证 dropped ACK + same-commandId replay；

7. 两台真机即可执行实际 lifecycle/network smoke；
8. 只有重大 milestone 才需要完整真人桌；
9. 新游戏模块可以复用 harness，不需要复制多人测试框架；
