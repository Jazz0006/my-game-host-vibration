# 微信客户端大厅与方桌 UI 实施基线

> 状态：**NORMATIVE — IMPLEMENTATION BASELINE**  
> 原冻结日期：2026-09-28；产品壳拆分路线同步：2026-09-29  
> 适用项目：`my-game-host-vibration`  
> 范围：两个 game-specific 微信小程序薄壳的入口页、房间大厅、通用方桌、人工/自动主持位、Ready/震动测试、房间管理入口。  
> 不覆盖：具体游戏 Setup、夜间/白天游戏内 UI、规则算法、网络协议、ClientSession/reconnect/runtime ownership。

## 1. 产品原则

微信小程序是主要玩家客户端。Lobby 不是成员列表页，而是游戏开始前就存在的**通用方桌**。

核心原则：

1. 尽量减少页面跳转；
2. 玩家加入后直接进入方桌大厅；
3. Lobby 只呈现当前真正需要的信息和操作；
4. 房间所有权、游戏主持角色、外围玩家身份彼此独立；
5. 每个小程序只对应一个固定游戏：工作名 `骏骏桌游-狼人` / `骏骏桌游-血染`；创建房间时固定 `gameType`，Lobby 不提供跨游戏切换；
6. 具体游戏配置只在点击“开始游戏”后进入该产品对应的 Setup；
7. 两个小程序共享同一套 ClientSession / transport / reconnect / room-management 基础，不复制网络或恢复实现；
8. 客户端只表达 UI intention / capability，不复制服务端游戏规则或秘密信息计算。

## 2. 入口页

不设置独立“加入房间”页面。

入口页同时提供：

```text
┌────────────────────────────┐
│       骏骏桌游-狼人 / 血染    │
│                            │
│      一起玩桌游，更轻松       │
│                            │
│       [ 创建房间 ]          │
│                            │
│ [ 加入房间 ] [ _ _ _ _ ]   │
│                            │
│ ───────────────────────── │
│  若存在可恢复房间：          │
│  [ 继续上次房间 ]           │
└────────────────────────────┘
```

规则：

- 房间号为 4 位数字，输入框直接位于入口页；
- 创建房间后直接进入 Lobby，不增加“创建成功”中间页；
- 通过微信分享邀请进入时，直接进入目标房间，不要求再次输入房间号；
- “继续上次房间”只在存在可恢复房间时显示。

## 3. Lobby 方桌是主界面

大厅采用通用方桌，不显示空座位，也不显示“当前人数”等可由桌面直接观察出的冗余信息。

房主视图只保留必要控制：

- 邀请朋友；
- 开始游戏；
- 设置入口；
- 直接拖动外围玩家调整顺序；
- 中央人工/自动主持位；
- 当前产品/游戏的固定标识（不作为可切换控件）。

普通玩家视图不显示座位说明、游戏详情或多余按钮；底部只保留一个 Ready 状态按钮。

## 4. 方桌布局基线

布局设计直接参考 `CampBoardGameHost` 当前成熟方桌机制，但不导入其 Android/runtime/game-specific ownership。

参考语义：

- 外围玩家按一个稳定的 clockwise `playerOrder` 排列；
- 视觉为适应手机竖屏的圆角矩形方桌，而不是固定人数模板；
- 座位沿圆角矩形完整周长按可用空间计算；
- 玩家数变化时重新计算整圈位置；
- 没有“空座位”实体；
- 新加入玩家默认 append 到 `playerOrder` 末尾；
- 渲染位置和拖拽命中应共享同一布局 authority；
- 玩家移动应有平滑动画。

已验证可参考的 CampBoardGameHost 设计位置：

```text
SeatingFirstSetupUi.kt
ClocktowerHostTableUi.kt
ClocktowerSquareTableUi.kt
ClocktowerHostTableLayout.kt
ClocktowerHostTableReorder.kt
```

其中值得继承的是**布局与交互思想**，不是 Clocktower 专属状态、角色信息或 Android Compose 实现本身。

## 5. 房主直接拖动玩家调整顺序

不提供“调整座位”按钮，也不进入编辑模式。

房主直接长按外围玩家卡并拖动：

```text
长按玩家
  -> 开始拖动
  -> 根据当前位置解析最近 ringIndex
  -> 其他玩家实时动画让位
  -> 松手
  -> 提交新的 playerOrder
```

排序语义采用 insertion/move，而不是简单 swap。

例如：

```text
A B C D E

把 B 拖到 D 的最终位置

A C D B E
```

普通玩家不能调整全桌顺序。

## 6. Ready 状态与震动测试合并

外围玩家状态必须能一眼看出：

- 未准备；
- 已准备；
- 连接异常/暂时离线（表现方式后续定稿）。

大厅不设置独立 Ready Check 页面，也不设置单独震动测试按钮。

普通玩家底部唯一主操作：

```text
[ 已准备好 ]
```

第一次进入 Ready 状态时同时触发一次震动能力测试，使“准备”动作承担夜间提醒设备校验。

Ready 是玩家属性，不是 Room phase：

```text
readyByPlayer[playerId] = true | false
```

不创建 `READY_CHECK` / `READY_TO_START` 等额外 Lobby 状态。

## 7. 中央区域：固定主持位 + 固定游戏身份

微信发布形态已经调整为两个 game-specific thin-client shells：

```text
骏骏桌游-狼人 -> gameType = werewolf -> 主持标签“法官”
骏骏桌游-血染 -> gameType = botc     -> 主持标签“说书人”
```

因此 Lobby **不再显示游戏单选列表，也不支持在房间内切换游戏**。创建房间时由当前小程序固定 `gameType`；客户端加入房间时若 gameType 不匹配，应显示明确的产品不匹配提示，而不是修改房间类型。

MG0D（2026-09-29）已完成该产品壳拆分：仓库只保留一份 `miniprogram/` shared shell source，构建生成 `wechat-build/werewolf` 与 `wechat-build/botc` 两个独立 Developer Tools 工程；产品配置分别固定名称、gameType、主持标签和固定游戏身份，Lobby 源码已删除 `selectedGame` / `PREVIEW_GAMES` / `onGameTap` 历史切换逻辑。

### 7.1 主持位

主持位始终存在。狼人产品显示 **法官**，BotC 产品显示 **说书人**。

默认主持方式为：

```text
Automatic
```

BotC 示例：

```text
┌──────────────────┐
│    📖 说书人      │
│       自动        │
└──────────────────┘
```

房主可以把一个外围玩家直接拖入主持位：

```text
ModeratorAssignment = Human(playerId)
```

该参与者随后从外围 `playerOrder` 中移除，但仍属于房间 participant。

房主也可以把人工主持人从中央拖回外围指定位置；完成后主持位恢复：

```text
ModeratorAssignment = Automatic
```

房主本人可以同时担任人工主持人；**Room Owner 与 Game Moderator/Storyteller 是独立职责与权限**。尤其在 BotC 中，真人说书人可获得游戏所需的秘密视图，但 Room Owner 不会因为拥有房间管理权就自动获得秘密魔典信息。

### 7.2 游戏标识

中央可以显示当前产品的固定游戏名称/图标作为信息，例如“狼人杀”或“血染钟楼”，但它不是控件，没有 `selectedGame` 状态，也不会触发 gameType 迁移。

## 8. “开始游戏”按钮职责

大厅底部“开始游戏”按钮始终存在。

它不承担游戏选择；当前游戏已经由小程序产品壳固定。

点击之后进入该产品对应的具体 Setup：

```text
Lobby
  -> 开始游戏
      -> currentProduct.game.setup
```

Blood on the Clocktower 示例：

```text
开始游戏
 -> 选择剧本
 -> 角色/Setup 配置
 -> 正式进入游戏
```

Werewolf 示例：

```text
开始游戏
 -> 狼人杀角色/规则配置
 -> 正式进入游戏
```

因此 Lobby 中不显示 Trouble Brewing、狼人数量、角色配置等具体游戏 Setup 内容。B0A 当前只建立 Trouble Brewing authoritative setup/view contract；真正的 BotC Setup 页面与首夜流程分别在后续 B0 UI / B0B slices 接入。

## 10. 普通玩家视图

普通玩家大厅只需要：

- 看见完整方桌；
- 看见所有外围玩家的 Ready 状态；
- 看见当前产品对应的固定游戏；
- 看见当前是自动主持还是某个真人主持；
- 看见房主标识；
- 操作自己的 Ready 状态。

普通玩家不能：

- 拖动全桌排序；
- 修改房间 gameType；
- 修改主持 assignment；
- 开始游戏；
- 执行房间管理。

## 11. 房间管理

房间低频管理不占据主 Lobby 操作区。

通过右上角设置进入，设置页面至少提供一个 **房间管理** Tab。

第一版最低要求：

- 移交房主；
- 将玩家移出房间。

Room Owner 权限与 Game Moderator 权限必须分离。移交房主不会自动改变人工说书人/法官 assignment。

踢出当前人工主持人时，系统必须得到确定结果；当前基线为移除该 participant 后主持位回退为 `Automatic`。

更完整的退出、解散、权限细节可在实现该 Tab 时继续定义，不在本 checkpoint 强行冻结。

## 12. Lobby 状态模型

Lobby 不建立 `seat_editing`、`ready_check`、`ready_to_start` 等 UI phase。

建议的最小房间数据语义：

```text
Room {
  ownerId
  participants[]
  playerOrder[]
  gameType              // fixed at room creation
  moderatorAssignment
  readyByPlayer
  connectionByParticipant
}
```

其中：

```text
ModeratorAssignment =
  Automatic
  | Human(playerId)
```

`participants` 是房间成员集合；`playerOrder` 是外围玩家环。人工主持人仍在 `participants` 中，但不在当前外围 `playerOrder` 中。

## 13. Ownership / implementation boundary

Lobby UI 不能成为新的规则 owner。

推荐职责：

```text
Room Runtime
  -> room membership / owner / selected game / moderator assignment
  -> ready / connection / ordering authoritative state

Shared client runtime / ClientSession
  -> authoritative projection / command / reconnect

WeChat shell
  -> render table
  -> collect tap/drag/ready intentions
  -> vibration capability
  -> lifecycle
```

具体游戏模块继续拥有：

- 游戏 Setup；
- 角色配置；
- 游戏规则；
- secret calculation；
- night/day flow；
- BotC storyteller intelligence。

## 15. 实施验收基线

未来开始微信客户端正式大厅 UI 时，至少应满足：

1. 入口页可直接创建和输入 4 位房间号加入；
2. 创建/加入后直接进入方桌 Lobby；
3. 方桌不渲染空座位；
4. 外围玩家由一个稳定 `playerOrder` 驱动；
5. 房主可长按拖动直接 reorder，无编辑模式；
6. Ready 状态在方桌上可见，Ready 操作同时完成震动测试；
7. 中央主持位始终存在，默认 Automatic；
8. 当前小程序固定一个 gameType，Lobby 不提供跨游戏选择或切换；
9. 房主可拖玩家进入/离开人工主持位；
10. “开始游戏”进入当前产品对应游戏的 Setup；
11. 设置页有房间管理 Tab，至少支持移交房主和踢人；
12. Room Owner / Moderator / Player 语义独立，BotC 真人说书人秘密视图不能泄漏给普通 Room Owner；
13. 两个小程序复用 shared client/runtime/backend，不复制 reconnect、identity、transport 或 recovery；
14. 不复制服务端规则、secret calculation 或 recovery policy 到微信 UI。
